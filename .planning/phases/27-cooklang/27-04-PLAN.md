<objective>
**Phase 27 — WAVE 3, PLAN 4 of the wave: BOUND THE PARSE.** A hardening plan, not a
feature plan. It carries no new user-visible behaviour.

**Why this plan exists.** T-27-01 (untrusted, model-shaped text reaching the
`@cooklang/cooklang` WASM parser) has now been mitigated **twice** and **independently
refuted twice**.

*Round 1* (`f29254b9`) added a predictive `maxCookMalformedTokens: 8` cap plus
`countMalformedCookTokens`, which tried to guess which prose the parser would object
to. Refuted in BOTH directions: a bypass (16 steps x 3 996 chars of `@a{1%}`, counted
**0** malformed, ~10 s parse, 143.7 MB report) and a false positive (a legitimate
536-byte pot roast using "Preheat the oven @ 325", "a 3 # chuck roast", "reduce ~ 10
minutes" counted 12 malformed and was REFUSED, although the real parser handled it in
13 ms with an empty report).

*Round 2* (`f7bcecb8`) escaped every metacharacter at the serializer so the `.cook`
contains only intended tokens **by construction**, deleted the predictive cap, and
added `findCookSourceDefect`, an output-integrity recognizer for the serializer's own
grammar. It **succeeded at what it targeted** — body-grammar escaping is complete, the
false-positive direction is genuinely fixed (14 realistic recipes all mint, including
`2% milk`, `70% dark chocolate`, `S&P`, `3-4 cloves`, `180°C (350°F)`, Dutch `± 200 g`,
CJK and `{filtered} water`), the nine caps are intact, and `parser.extensions = 0` was
confirmed a genuine win (sections, cookware, multi-timers, named timers, notes, ranges,
frontmatter, comments and servings scaling all byte-identical to the default mask; it
also fixed live text corruption where `180°C` rendered as `180 °C` and `1.50 kg` as
`1.5 kg`). But it was refuted on **three new holes** — H1 (an unconstrained frontmatter
recognizer: a 65 417-byte input parses for **24 557 ms / 38 511 ms** with a
131 218-byte "recursion limit exceeded" report), H2 (a **9-byte** input still panics the
WASM with `RuntimeError: unreachable`), and H3 (an undocumented normalization that
**silently deletes user text**).

**THE DECISION THIS PLAN IMPLEMENTS (Kiran).** Three rounds of "make the input
recognizer complete" each discovered a sub-grammar the last did not know about. The
parser's failure modes are unbounded — quadratic diagnostics, YAML recursion blowups,
`unreachable` on nine bytes. So: **bound the parse itself**, so that recognizer
completeness stops being load-bearing. The escaping and `findCookSourceDefect` stay as
**defence in depth**; the hard guarantee comes from a real resource bound on the parse,
not from an input-shape predicate. **H1, H2 and H3 are fixed at their roots as part of
this work.**

**Output.** A pooled child process that is the only thing in the repo which imports
`@cooklang/cooklang`; a wall-clock bound enforced by `SIGKILL` from the parent and a
heap bound enforced by the child's own `--max-old-space-size`; an `async`
`parseCookSource` / `buildCookPayload` / `buildCookFromExtraction`; a frontmatter
recognizer restricted to the serializer's closed key set; a serializer that cannot emit
a whitespace-only amount or unit; and a `splitFragment` that slices by the matched span
instead of `ref.name.length`.

**THE NEVER-BROKEN GUARANTEE, RESTATED.** Every import that succeeds today must still
succeed, with the same ingredient rows, the same step rows and the same shopping-list
behaviour. A refusal, a bound hit or a child crash costs the user nothing: `cook_source`
NULL, full legacy projection, import succeeds. On the read path a failure degrades to
the legacy render, never a 500 and never a hang. Anything that makes an import fail,
lose an ingredient, lose a step, or hang a recipe page is a defect of this plan.

**KNOWN AND ACCEPTED, DO NOT RE-OPEN.** CR/LF in prose folds to a space (documented;
Cooklang has no in-step line break, so a raw newline is structural injection). A
two-paragraph step therefore becomes a run-on line. Kiran is aware. Record it in the
SUMMARY; do not change it.

**Hard scope fence — W4/W5/W6 stay untouched:** the web/mobile token renderer, the
multi-timer UI, the `cookTokens ? tokenRenderer : legacy` client fork (W4); the `0042`
backfill, `cook_confidence`, the confidence gate, the review queue and the repair tool
(W5); `0043` NOT-NULL and deleting `unit-converter.ts` / `applyIngredientLinkMarkup` /
`createIngredientLinkCandidates` / `SmartInstruction` / the timer-keyword scan (W6).
D-1..D-8, D-27-W1-*, D-27-W2-* and D-27-W3-* are LOCKED — implement them, do not
relitigate.

## Decisions taken FOR this plan — every one backed by a measurement taken on THIS tree

All measurements below were taken on LXC 110, Node **v22.22.3**,
`@cooklang/cooklang@0.18.7`, `extensions = 0`, using the real
`CooklangParser` wrapper (`index.js` line 173: `parse(input, scale)` returns
`[CooklangRecipe, report]` and internally makes **three** WASM calls — `parse`,
`group_ingredients`, `group_cookware`). Throwaway rigs lived under `/tmp/cookbound/`
and were never committed. **The executor must re-run the equivalent assertions as
tests; these numbers are the design justification, not the proof.**

### D-27-W3B-01 — The bound is REAL and it is ACHIEVABLE: `terminate()`/`SIGKILL` interrupts a running WASM parse
The premise that had to be tested first, because if a synchronous WASM parse cannot be
interrupted, option B is unworkable and this whole plan is void. **It is interruptible.**

| probe | result |
|---|---|
| `worker.terminate()` called 500 ms into the H1 payload's 24 s parse | resolved in **4 ms**, exit code 1 |
| process CPU accounting for 3 s after `terminate()` resolved | **+0 ms** — the thread is genuinely dead, not detached and burning |
| `child.kill("SIGKILL")` 250 ms into the same parse | child exited in **16 ms** |

Both mechanisms work. V8 honours a termination request at WASM loop back-edges, and
`SIGKILL` needs no cooperation at all. **Option B is workable. Nothing in this plan
rests on an unmeasured assumption about cancellability.**

### D-27-W3B-02 — Isolation mechanism: a POOLED CHILD PROCESS. Not a fresh isolate per parse, not `worker_threads`.
Three candidates were measured end-to-end on a realistic **448-byte** `.cook` (the five
committed fixtures serialize to 225–506 B), with the token projection done inside the
isolate so that only plain JSON crosses the boundary.

**(a) Instantiation is far too expensive to pay per parse.**

| cost | measured |
|---|---|
| `import("@cooklang/cooklang")` (WASM compile + instantiate, 2 090 790-byte binary) | **15–20 ms** |
| `new CooklangParser()` first / subsequent | 6.2 ms / ~0.35 ms |
| first `parse()` (JIT warm-up) | **28.7 ms** |
| warm `parse()` of a 74-byte source | 0.09 ms |
| **fresh `worker_threads` worker per parse**, spawn -> import -> parse -> reply | **145.6 / 152.4 / 214.7 ms** (min/med/max, n=10) |
| **fresh `child_process.fork` per parse** (ready alone) | **116–134 ms** |

A fresh isolate per parse costs **~150 ms** and would be immune to poisoning, but it is
**~120x** the pooled cost and would put 150 ms on every recipe fetch. **A pool is
mandatory.** Recorded so a later wave does not "simplify" to a fresh worker.

**(b) Pooled round trip — child process beats worker threads, and both are cheap.**

| mechanism (448 B, n=300, warm) | p50 | p95 | p99 |
|---|---:|---:|---:|
| **TODAY, in-process synchronous parse** | 0.643 ms | 3.097 ms | — |
| pooled `worker_threads` | 1.229 ms | 5.385 ms | 7.322 ms |
| **pooled child process (CHOSEN)** | **0.965 ms** | **1.506 ms** | **3.508 ms** |

The child process is not merely competitive, it is **more stable at the tail** (p95
1.506 ms vs 5.385 ms) because it does not share a heap or a GC with the request-serving
event loop. The worker thread's own p95 is dominated by contention with the parent.

**(c) The decider — `worker_threads` CANNOT be given a safe memory bound.**
`resourceLimits` works correctly for ordinary JS: a runaway pure-JS allocation in a
worker with `maxOldGenerationSizeMb: 64` produced a clean, contained
`ERR_WORKER_OUT_OF_MEMORY` and the parent survived. But on the **actual payload class
in question** it does not:

```
worker_threads, resourceLimits { maxOldGenerationSizeMb: 64 }, round-1 bypass payload
  -> FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory
  -> node::OOMErrorHandler -> v8::internal::V8::FatalProcessOutOfMemory
  -> stack: v8::internal::JsonParser<unsigned short>::ParseJson <- Builtin_JsonParse
  -> THE ENTIRE NODE PROCESS ABORTED. The parent did NOT survive.
```

The WASM binding hands its result back as a JSON string that `JSON.parse` deserializes,
and that allocation happens inside a V8 builtin where V8 cannot unwind to the graceful
per-worker OOM path — so it escalates to a process-wide abort. **A memory bound that,
when hit, kills the web server is not a bound; it is a larger incident than the one it
prevents.** The same payload against a child process:

```
child_process.fork, execArgv ["--max-old-space-size=192"], same payload
  -> EXIT code=null signal=SIGABRT after 7 855 ms
  -> PARENT ALIVE. Fatal OOM contained to the child.
```

**Resolution: a pooled child process.** It is the only measured option that provides
BOTH bounds as genuine, independent, enforceable guarantees — `SIGKILL` for time (OS-
guaranteed, needs no V8 cooperation) and `--max-old-space-size` for memory (contained to
the child) — at equal or better latency than `worker_threads`.

**Deviation from the brief, stated plainly:** Kiran's framing asked for `resourceLimits`.
The measurement above says `resourceLimits` is the one thing that must NOT be relied on
here. The child process delivers exactly the property `resourceLimits` was asked for,
which `resourceLimits` itself does not.

### D-27-W3B-03a — **THE PRIMARY GATE IS CPU TIME, NOT WALL CLOCK.** `cookParseCpuMs: 1_500`, `cookParseWallCeilingMs: 8_000`, `cookParseHeapMb: 256` unchanged
**DIRECTOR DECISION, 2026-07-26. Supersedes D-27-W3B-03.** Recorded here because it
overrides a locked decision and no executor may retune it back.

**Why the three options the SUMMARY offered were all REJECTED.** §3b offered
(1) raise the wall-clock bound to 2 000 ms, (2) ship 1 000 ms and watch, (3) accept the
loss. **All three pick a different point on the same wall-clock axis, and each flips
again on a busier box.** Kiran's standing directive is no bandaids, root cause only.

**Root cause.** The bound measured WALL CLOCK, which conflates the threat (unbounded
computation) with unrelated host load. A pathological parse burns CPU. A legitimate
parse under contention burns the same small CPU and only inflates in ELAPSED time.
Measured on LXC 110, child + ten spinners pinned to one core:

| worst ACCEPTED shape | wall idle | wall starved | **CPU idle** | **CPU starved** |
|---|---:|---:|---:|---:|
| 64 KiB of `@a{1%g} ` | 351-449 ms | **4 096-5 085 ms** | 328-373 ms | **328-373 ms** |
| `"#p " x 21845` | 483-830 ms | **5 537-6 264 ms** | 453-506 ms | **452-506 ms** |

Wall clock inflated **7.5x-11.6x**; the CPU figure moved by **±3%**. That is the axis
the bound belongs on.

**Why now and not "watch it in production".** **W6 makes `cook_source` NOT NULL**, so a
refusal that costs only a legacy render today becomes an **IMPORT FAILURE** then. A
contention-flaky bound is a latent W6 defect and must be fixed, not tuned.

**The mechanism.** The child cannot self-police — the synchronous WASM parse can never
check a timer, which is the original problem this whole pivot exists for — so the
PARENT measures it. It samples `/proc/<pid>/schedstat` field 1 (`sum_exec_runtime`, in
NANOSECONDS) every `cookParseCpuPollMs` and `SIGKILL`s the child once
`cookParseCpuMs` is spent. `schedstat` over `/proc/<pid>/stat`'s `utime`+`stime`,
measured: ns resolution instead of 10 ms USER_HZ ticks (and no `sysconf(_SC_CLK_TCK)`
assumption, which Node exposes nowhere); it reports the MAIN THREAD, which is where
100% of the hostile computation is, whereas the thread-group figure also charges V8's
parallel GC helpers — **690 ms against a 346 ms main thread for one and the same
parse**, i.e. a function of how many cores happen to be free, which is the exact
coupling this decision removes.

**Poll cost: 30 µs per sample** (measured, 20 000 iterations), and **ZERO samples for
any normal parse** — the first sample is 25 ms out and a pooled round trip is
~0.97 ms, a 64 KiB realistic recipe ~15 ms. Overshoot is one interval: measured
1 520 ms against a 1 500 ms budget.

**The budgets, from measurement.**
- **`cookParseCpuMs = 1 500`.** A sweep of every shape that reaches the 64 KiB
  `cook_source` cap — the two above plus timers, prose, headings, 200x4 000-char
  steps, 600 ingredient refs, real frontmatter — puts the worst LEGITIMATE CPU cost at
  **506 ms**. 1 500 ms is **2.96x** over it, ~88x over a realistic recipe, ~2 500x over
  a fixture. Hostile CPU: H1 **22 759 ms**, `"#" x 8192` **12 222 ms**, round-1 bypass
  **4 895 ms** — all killed after 1 500 ms.
- **`cookParseWallCeilingMs = 8 000`** — a BACKSTOP, not a computation bound. Its only

  gate is structurally blind to because the counter never advances. Generous because a
  blocked-but-idle child is not a DoS amplifier: it occupies one pool slot,

  terminate-and-replace disposes of it. 8 000 ms is 9.6x the worst legitimate IDLE wall
  clock (830 ms) and still above the 6 264 ms measured under 11.6x single-core
  starvation — a condition harsher than four-core LXC 110 can present.
- **`cookParseHeapMb = 256` UNCHANGED, and MORE load-bearing.** Per §3 it fires at
  6-12 s rather than the predicted ~285 ms, so it is not the gate that fires first —
  but it is the only thing between a hostile row and the measured 839 MB-1.65 GB
  balloon now that the wall ceiling is 8 s rather than 1 s.
- **`cookParseReadyTimeoutMs = 2 000` is now NAMED rather than derived.** It used to be
  `cookParseQueueTimeoutMs + cookParseTimeoutMs`; with the parse bound becoming an
  8 000 ms backstop that derivation would silently have stretched the cold-spawn wait

**The nine `COOK_LIMITS` are untouched and `maxCookMalformedTokens` stays dead.**

### D-27-W3B-06 — H1 root fix: the frontmatter recognizer accepts the serializer's CLOSED key set, not arbitrary YAML
`FRONTMATTER_LINE = /^[A-Za-z][A-Za-z0-9._-]*: .*$/`
(`packages/shared-server/src/cooklang/limits.ts:236`, used at `:424`) constrains neither
the key nor the value, so **arbitrary YAML passes both gates**. Measured consequences,
all with `findCookSourceDefect` returning `null`:

| input | bytes | parse time | report |
|---|---:|---:|---:|
| `---\na: ${"[".repeat(65400)}\n---\nstep\n` | 65 417 | **24 557 ms** / **38 511 ms** (two runs) | 131 218 B, "recursion limit exceeded" |
| balanced 30 000-deep `[`/`]` | 60 017 | 8 256 ms | diagnostics |
| balanced 25 000-deep `[`/`]` | 50 017 | 4 838 ms | diagnostics |
| `{`-nesting variant | ~60 000 | 10 489 ms | diagnostics |
| `title: @@@@ ####` | small | fast, but **passes** and produces diagnostics |
| `a: &x [*x]` (YAML anchor + alias) | small | fast, but **passes** and produces diagnostics |

A **monotone family**, not a lucky point. **Root fix:** the recognizer must accept
EXACTLY the shape the serializer emits and nothing else. The executor reads the
serializer's frontmatter emission (`packages/shared/src/cooklang/serialize.ts`,
`quoteYaml` at `:207` and the `.map(({ key, value, raw }) => \`${key}: ${raw ? value : quoteYaml(value)}\`)`
at `:235`) and derives the closed key set from the code — it must NOT be guessed, and the
test must FAIL LOUDLY if the serializer ever emits a key the recognizer does not know
(a two-way assertion, not a one-way allowlist). The recognizer shape:

```
frontmatter := "---" NL ( line NL )* "---" NL
line        := KEY ": " VALUE
KEY         := one of COOK_FRONTMATTER_KEYS   // a closed `as const` set, exported from the SERIALIZER
VALUE       := quoted | numeric
quoted      := '"' ( any char except '"' or '\' or a control char | '\\' | '\"' )* '"'
numeric     := "-"? DIGIT+ ( "." DIGIT+ )?    // exactly what String(Number(x)) can produce
```

Consequences that make this sound in both directions: `[`-floods, `{`-floods, anchors
(`&x`), aliases (`*x`), block scalars (`|`, `>`), flow sequences, flow maps, tags (`!!`),
multi-document markers, comments, tabs, unquoted values, an empty value, a duplicate key,
a key not in the closed set, an unterminated quote, a raw `"` or `\` inside a quoted
value, and any control character are **all rejected with a named defect code**. And
`title: @@@@ ####` is rejected because the serializer would have emitted
`title: "\@\@\@\@ \#\#\#\#"` — quoted and escaped. `a: &x [*x]` is rejected on both the
key (`a` not in the closed set) and the value grammar.

Additionally the recognizer must cap the frontmatter itself: **at most one** `---...---`
block, and it must be the **first** thing in the source; at most
`COOK_LIMITS.maxRecipeNameChars` for a `title` value and a hard cap on the number of
frontmatter lines (the closed key set's size). A source whose frontmatter block is
larger than the sum of its permitted key/value maxima is a defect by arithmetic, which
is what actually kills the whole H1 family at the door.

**This fix is defence in depth, NOT the guarantee.** Every H1 input above must ALSO be
proven bounded with `findCookSourceDefect` stubbed to `null` — that is the test that
proves the pivot worked.

### D-27-W3B-07 — H2 root fix: a whitespace-only amount and/or unit, for `@`, `~` and `#`
`@a{ %g}` — **8 bytes** — passes both gates and hits `RuntimeError: unreachable` in the
WASM. Confirmed on this tree, together with `~a{ %m}`, `#a{ %g}`, `@a{ %g}` without a
trailing newline, and `~a{ % }`. `f7bcecb8` fixed the **empty**-amount case and missed
the **whitespace-only** case.

**Measured mitigating fact, recorded because the brief's phrasing invites the opposite
worry:** the trap does **not** poison the parser. After a trap, the SAME
`CooklangParser` instance, a NEW `CooklangParser` from the same module, and a
cache-busted module import all parse a good source correctly. So severity stays low —
but it is precisely the panic class round 2 claimed to close, and a panic in a compiled
Rust binary reached from a prompt-injection surface is not something to leave open.

**Root fix, two-sided:**
- **Emission:** the serializer must never emit a token whose amount or unit is
  whitespace-only. The existing empty-amount guard is extended from "is it empty" to "is
  it empty **after trimming**", and applied to the amount AND the unit AND for all three
  sigils the serializer can emit. If, after trimming, a token has no usable amount, it
  degrades exactly as an amount-less token does today (`@name` with no braces) — it must
  NOT drop the reference and must NOT change the projection.
- **Recognition:** `findCookSourceDefect`'s `{amount%unit}` body validator rejects a
  whitespace-only amount and a whitespace-only unit with a named defect code, for `@`,
  `~` and `#`.
- The executor must first establish whether the serializer emits `#cookware` tokens **at
  all**. If it does not, the recognizer still rejects the `#` form (a `#` token in a
  serializer-authored source is by definition not serializer-shaped) and the emission-side
  fix is a no-op for `#` — say so explicitly in the SUMMARY rather than silently
  implementing half of it.

### D-27-W3B-10 — Pool shape: lazy, size 2, terminate-and-replace, request-queue bounded
- **Lazy.** No child is spawned until the first parse, so a process that never touches a
  `.cook` pays nothing (`fork` -> ready costs 116–134 ms, and it must never land on a
  request that could have avoided it).
- **Size 2** by default (`NORISH_COOK_PARSE_POOL_SIZE`). At 0.97 ms per parse one child
  serves ~1 000 parses/s, so 2 is throughput headroom; the reason for 2 rather than 1 is
  **head-of-line blocking** — a single bounded-out parse would otherwise delay every
  queued read by up to 1 000 ms. With 2 children a single poisoned row cannot stall the
  read path. Worst-case transient memory is `2 x 256 MB`; record that in the SUMMARY as
  an operational number for LXC 110.
- **Terminate and replace, never reuse.** A child that hit the time bound, hit the heap
  bound, exited, errored, or returned a malformed envelope is `SIGKILL`ed and replaced.
  The replacement cost (116–134 ms) is paid **off** the request path — the request that
  triggered it has already been answered with `null`. Justified even though the
  `unreachable` trap was measured to be recoverable (D-27-W3B-07): a compiled binary that
  has just trapped is not a thing to keep serving requests from, and the cost is zero to
  the user.
- **Bounded request queue.** A request that cannot get a child within
  `cookParseQueueTimeoutMs` (default = the parse timeout) resolves `null` with a
  `reason: "pool-saturated"` log rather than queueing without limit. Saturation degrades
  to the legacy render; it never hangs a request and never grows unboundedly.
- **Spawn failure is not an error path for the user.** If `fork` fails or the child never
  reports ready, `parseInPool` resolves `null` with an error-level log. `cook_source`
  stays NULL, the legacy projection is written, the import succeeds.
- The pool exposes `shutdownCookParsePool()` for `afterAll` in tests and for graceful
  process shutdown, so a leaked child cannot hang a vitest run or a container stop.

### D-27-W3B-11 — `parse(src, scale)` survives the boundary

re-opening the boundary in W4.

### D-27-W3B-12 — The "parser never invoked" proof MOVES from a WASM spy to a POOL spy
`packages/shared-server/__tests__/cooklang/limits.test.ts:43-44` proves "0 parse calls on
breach" with `vi.mock("@cooklang/cooklang", ...)` delegating to `vi.importActual`. Once

**Resolution:** the invariant being proven is unchanged in substance and gets *stronger*

enforceable by a static check: the accompanying test asserts that
`@cooklang/cooklang` is imported by **exactly one** source file. Every existing
`toHaveBeenCalledTimes` assertion in that suite must be re-pointed, not deleted — a
deleted spy assertion is a deleted guarantee.

### D-27-W3B-13 — The recognizer STAYS, and the docblocks must stop claiming it is the guarantee
`findCookSourceDefect`, the byte cap and the serializer escaping all stay, checked
**before** the pool is asked: they keep a known-bad source from costing a process round
trip at all, they keep the diagnostics-based confidence signal W5 wants, and they are the
reason a legitimate recipe never comes near a bound. **But they are no longer the
guarantee.** `limits.ts`'s current docblock says the recognizer "turns the time bound into

architecture: **the bound is the guarantee; the recognizer is defence in depth; a future
gap in the recognizer is a quality issue, not a security incident.** This rewrite is a
