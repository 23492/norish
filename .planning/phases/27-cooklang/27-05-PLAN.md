<objective>
**Phase 27 — WAVE 4: THE CLIENT TOKEN RENDERER.** The first wave whose deliverable is
user-visible, and the first that touches `apps/`.

**What lands.** Recipe detail and cooking mode, on web and on mobile, render each step
from the recipe's own `.cook` — the `cookTokens` DTO projection that W1 contracted, W2
shipped through the permission-scoped read path and W3/W3B started minting for real —
instead of scanning the step's prose for ingredient names. In-step amounts stop being
a heuristic name match and become the recipe's authored truth. Cooking mode gains
**concurrent named timers** driven by `~name{n%unit}` tokens: the pasta+sauce case,
which the keyword scan structurally could not deliver because it produces a duration
and no name.

**What this wave deliberately does NOT do, and why.** It does not delete
`applyIngredientLinkMarkup`, `createIngredientLinkCandidates`, `SmartInstruction` or
the timer-keyword config. Live currently holds **6 recipes, 0 with `cook_source`**
(`STATE.md`, 2026-07-27 cutover). Deleting the heuristic today would blank every
existing recipe's steps. `27-ARCHITECTURE.md` §7 is explicit: W4 deletes the heuristic
runtime path **where `cook_source` is present**, W5's backfill takes coverage to 100%,
and W6 deletes the symbols and the transitional fork. D-7 permits the tokens-else-old-path
fork "ONLY during the migration window" — this wave is that window. See D-27-W4-01.

**Output.** A pure token render model in `@norish/shared/cooklang` consumed by both
clients; a conditional token branch in the web renderer, the recipe-detail step list and
cooking mode; named concurrent timers wired into the existing `useTimerStore`; mobile
parity including the `formatUnit` wiring it never had; and a proof suite that the
heuristic is not merely unused on the token branch but *uncalled*.

**THE NEVER-BROKEN GUARANTEE, RESTATED FOR THIS WAVE.** A recipe with no `cookTokens`
must render **exactly** as it does today — the legacy branch is the common path, not the
exception (`waves/W3-SUMMARY.md`, "What W4 can now assume"). Anything that changes the
appearance, the chip behaviour, the heading rendering or the timer behaviour of a
`cook_source IS NULL` recipe is a defect of this plan. Anything that makes a token-bearing
recipe render fewer steps, lose prose, or disagree with its own ingredient list is a
defect of this plan.

**KNOWN AND ACCEPTED, DO NOT RE-OPEN.** (a) `setActiveSystemForRecipe` NULLs
`cook_source` on a metric↔US switch (`recipes.ts:1156`), so switching systems drops a
recipe back to the legacy render until W5 re-mints. That is W5/W6 territory and is
already a recorded W6 prerequisite. (b) A `cook_source` is always in the recipe's own
`systemUsed` — the same CASE expression guarantees it — so the renderer needs no
per-system token selection. (c) CR/LF in step prose folded to a space at serialize time
(W3B); a two-paragraph step is a run-on line on the token branch. Kiran is aware.
</objective>

## Decisions taken FOR W4 in this plan (new; the executor implements these, does not relitigate them)

#### D-27-W4-01 — The heuristic is deleted from the DEFAULT, not from the tree
The token branch never calls `createIngredientLinkCandidates`, never calls
`applyIngredientLinkMarkup` and never calls `parseTimerDurations`. The symbols and the
legacy branch survive until W6. Rationale: `27-ARCHITECTURE.md` §7 assigns "delete
heuristic **runtime** path where `cook_source` present" to W4 and "delete ... the
heuristic `ingredient-links` markup, the transitional read-fork, timer-keyword scan" to
W6; D-7 permits the fork only until backfill reaches 100%; live has 0 recipes with
`cook_source`. Deleting now would blank every existing recipe. **The deletion this wave
owes is a PROOF OF NON-INVOCATION, not a `git rm`.**

#### D-27-W4-02 — The render model is a PURE module in `@norish/shared/cooklang`
Not a React component, not a web-local helper. Both clients need identical section,
step-numbering and scaling semantics; mobile has no React-render test harness and can
only test pure modules (its whole `__tests__` tree is node-env vitest); `@norish/shared`
is already on both bundles and already hosts the serializer this is the twin of. The
`./cooklang` subpath already exists in `packages/shared/package.json`, so **no export-map
change is needed** — which removes half of the hoisted-linker hazard. The other half
still applies: `render.ts` is a NEW file, so `cp -a packages/shared/src/. node_modules/@norish/shared/src/`
after creating it, or cross-package resolution goes stale (`27-CONTEXT.md` hazards).

#### D-27-W4-03 — Servings scaling is applied client-side to ingredient amounts only
`resolveCookRenderSteps(tokens, { baseServings, servings })` reproduces
`recipe-detail-context.tsx:332` **CHARACTER FOR CHARACTER**:

```ts
Math.round((amount / baseServings) * servings * 10000) / 10000
```

**Do NOT pre-compute a `scale` float and multiply by it.** `amount * (servings / baseServings)`
is a DIFFERENT IEEE-754 expression from `(amount / baseServings) * servings` and the two
diverge in the last ulp on repeating decimals — which is exactly the drift R3 forbids and
what the "never disagree by a digit" truth rules out. The options bag therefore carries the
two servings numbers, never a ratio. It also mirrors :332's guards exactly: `amount == null`,
`Number.isNaN(amount)` or `amount <= 0` returns the amount UNSCALED, and `baseServings` falsy
(0/null) is treated as no scaling — not as a divide-by-zero producing `Infinity`.
Timer amounts are NOT scaled (Cooklang does not
scale timers; a doubled recipe does not boil pasta twice as long). The rejected
alternative — re-parsing server-side with `parseCookSource(src, units, scale)` on every
servings change — would put a WASM parse on an interactive hot path, which T-27-01
forbids; the pool exists precisely so that never happens. Our serializer emits only
plain (scalable) quantities, never Cooklang's fixed `=` form, so multiplication is
faithful.

#### D-27-W4-04 — Units render through `formatUnit`; mobile gets the wiring it lacked
Token `unit` is a canonical norish unit ID (D-8, and stated in `cook-tokens.ts`'s own
header), never a display label. Web already has `useUnitFormatter` (`apps/web/hooks/use-unit-formatter.ts`).
Mobile has none and prints raw units (`recipe-ingredients.tsx:153`), so it gains
`use-units-query.ts` (a 3-line delegation to the existing `sharedConfigHooks.useUnitsQuery`,
which `createConfigHooks` already provides) plus a `use-unit-formatter.ts` wrapper over
`useMobileLocaleSettings()`. This is required by `27-ARCHITECTURE.md` §2.1 ("in-token
`name + formatUnit(amount,unit)`") and is ~15 lines. Mobile's *ingredient list* is NOT
retrofitted — that is a separate, app-wide change and is out of W4.
**Note the intended behaviour change:** today's heuristic chip prints the raw canonical
unit (`formatIngredientLinkAmount` joins amount + unit verbatim). The token chip prints
the localized unit. That is the architecture's instruction, not a regression.

#### D-27-W4-05 — Headings come from `CookStepTokens.section`
Web has TWO heading implementations and both keep their *visual* semantics while
changing their *source* on the token branch: cooking mode's sticky heading chip
(`cooking-mode-steps.ts:40`, heading applies to following steps) and the detail list's
standalone `<h3>` row (`readonly-steps-list.tsx:120-134`). Mobile has two more
(`recipe-steps.tsx:65`, `cook-mode-steps.tsx:51`). On the token branch a heading is
emitted at a **section boundary** (`isSectionStart`), which reproduces both semantics
from one model. The `#`-sniffing code stays for the legacy branch; W6 removes it.

#### D-27-W4-06 — Named timers reuse the existing timer stores; no new subsystem
Both `apps/web/stores/timers.ts` and `apps/mobile/src/stores/timers.ts` already hold an
array and tick every running entry, so **concurrency already exists**. What is missing is
a *name*: `smart-markdown-renderer.tsx:70` and mobile's `smart-text.tsx` both hard-code
`` `Step ${n} Timer` ``. Token timers therefore reuse `addTimer` unchanged, with
id `${recipeId}-s${stepIndex}-${tokenIndex}` (no `-t` infix; distinct per token, so two
timers in one step coexist) and `label = token.name ?? t("timer.step_fallback_label", { step })`. The
hard-coded English label moves into `common.timer.step_fallback_label` across all 12
locales — the brief's i18n requirement, and it is used by the legacy branch too.

#### D-27-W4-07 — the notification identity becomes per-timer — **and the two clients are NOT symmetrical**
**Web — a real collapse, fix it.** `apps/web/stores/timers.ts:31` passes a FIXED
`tag: "timer-complete"` to `registration.showNotification`. The Notification API replaces a
displayed notification with the same `tag`, so two concurrently completing timers collapse
into ONE OS notification. With unnamed keyword timers that was invisible; with named
concurrent timers it makes the wave's headline feature user-visibly wrong ("pasta" and
"sauce" finish, you get one notice). Fix: `tag: timer.id`. That is TWO lines, not one — the
local `showTimerNotification(timer: { label: string; recipeName?: string })` signature must
also gain `id: string`. Its only call site (`timers.ts:198`) already passes the whole `Timer`,
so no caller changes.

**Mobile — the premise an earlier draft asserted is FALSE; do NOT "fix" it the same way.**
`apps/mobile/src/stores/timer-notifications.ts:33` does **not** pass a `tag`. It passes
`categoryIdentifier: "timer-complete"` to `Notifications.scheduleNotificationAsync` — that is
expo's NOTIFICATION CATEGORY (the action-button set), not a dedupe key, and expo does not
collapse on it: every `scheduleNotificationAsync` call already yields its own notification.
Overwriting `categoryIdentifier` with a timer id would DELETE the category and fix nothing.
The mobile change is therefore additive: pass the top-level
`identifier: timer.id` on the `scheduleNotificationAsync` argument (a stable, addressable id
so a specific timer's notification can later be dismissed) and leave `categoryIdentifier`
exactly as it is. Widen the `showTimerNotification` param type with `id: string`; its call
site (`stores/timers.ts:160`) already passes the whole timer.
(The store's hard-coded English `"Timer complete!"` body is a
**pre-existing** defect — `common.timer.notification_body` already exists but a zustand
store cannot call `useTranslations`. Explicitly OUT of scope; record it as a follow-up,
do not fix it here.)

#### D-27-W4-08 — The public share page keeps the legacy renderer
`getShared` outputs `PublicRecipeViewSchema`, which has no `cook*` field, and never calls
`withCookTokens`. Shipping tokens to an unauthenticated surface is a NEW read surface with
its own permission question that no phase artefact has scoped. `ReadonlyStepsList` and
`SmartInstructionLike` therefore gain an **optional** token prop, so
`PublicSmartInstruction` and `share-recipe-steps.tsx` are byte-for-byte unchanged.
Recorded as deferred, not dropped: "public `.cook` token surface" belongs with the
`.cook` import/export UX already deferred to Phase 31 (§9).

#### D-27-W4-09 — Token chips reuse the existing highlight contract, unchanged
The token chip emits the SAME markup the heuristic emitted —
`[label](norish-ingredient:<encodeURIComponent(key)>)` with
`key = getIngredientLinkCandidateKey({ ingredientName, systemUsed })` — so
`use-ingredient-link-highlight.ts`, the `data-ingredient-link-key` anchors in
`readonly-ingredients-list.tsx` and the press-to-scroll behaviour keep working with ZERO
change. The token `name` and the projection row's `ingredientName` were derived from the
same `.cook` by the same `normalizeIngredientLinkName`, so the key matches by
construction. If it ever does not, the chip degrades to the existing non-interactive
styled `<span>` (`smart-markdown-renderer.tsx:125-129`) — the behaviour that path
already has for an unknown candidate.

#### D-27-W4-10 — Mobile gets token parity, not a new test framework
Mobile has no `@testing-library/react-native`, no jsdom, no setup file. Per the repo's
own pattern (`recipe-actions-menu-share.ts` — component logic extracted into a pure
module, deps injected), all token logic lands in pure modules tested under the existing
node-env vitest and the RN components stay thin. Adding an RN render harness is a tooling
change W4 does not need.

#### D-27-W4-11 — The token branch REUSES `SmartMarkdownRenderer` / `SmartText` by feeding it token-derived MARKUP
Not a parallel renderer. A new component would have to re-earn `transformMarkdownUrl`'s
scheme allowlist, the `[Name](id:<uuid>)` recipe cross-link, the heading rules, the
markdown-label escaping and the XSS posture that `smart-markdown-renderer.tsx` already
owns and is tested for. Instead `cookStepToMarkdown` emits the SAME markup shape the
heuristic used to produce, and the pipeline below that point is untouched. This also
keeps markdown working ACROSS a step (bold/italic spanning an ingredient ref), which a
per-token plain-text renderer would break by construction. What gets bypassed is the
**scan**, which is exactly the thing W4 is chartered to kill.

#### D-27-W4-12 — Two pure helpers MOVE DOWN into `@norish/shared`, per the D-27-W1-04 precedent
`getIngredientLinkCandidateKey` and the `MARKDOWN_LABEL_ESCAPE` label escaper are needed
by the pure render model, and `@norish/shared` may not import `@norish/shared-react`
(`FORBIDDEN_EDGES`, `pnpm deps:cycles`). They move into
`packages/shared/src/lib/ingredient-token.ts` and `ingredient-links.ts` **re-exports
them** — zero behaviour change, zero duplication, nothing deleted, exactly the move
D-27-W1-04 already made for `normalizeIngredientLinkName`/`formatTokenAmount`.
Likewise `timer-parser.ts` exports its keyword→multiplier resolution
(`timerUnitSeconds`) and `parseTimerDurations` is refactored to call it, so token timer
units resolve through the SAME multilingual `timerKeywords` config with the same
`?? 60` (minutes) fallback, rather than a second copy of that table.

**One hardening the token path needs and the prose path does not.** `parseTimerDurations`
builds its map with `keywords?.hours ?? ["hour","hours","hr","hrs","h"]` etc.
(`timer-parser.ts:38-40`) — a configured list REPLACES the built-in one. That is right for
scanning prose, which is written in the deployment's language. It is WRONG for a token unit:
`CookTimerToken.unit` is "a Cooklang TIME unit (`minutes`, `hours`) — NOT a norish canonical
unit" (`packages/shared/src/cooklang/types.ts:22`), authored by our serializer or carried in
from an imported `.cook`, and it is not localized. On a deployment whose `timerKeywords.hours`
is configured to e.g. `["uur"]`, `~{2%hours}` would miss every group and take the `?? 60`
minutes fallback — **a silent 60× error**. So `timerUnitSeconds(unit, keywords)` resolves
against the configured lists UNIONED with the built-in English defaults (config wins on a
collision), and `parseTimerDurations` keeps calling it with its existing replace semantics via
an explicit flag. `render.test.ts` pins the union with a case whose `keywords.hours` omits
English and whose token still resolves `hours → 3600`. `timer-parser.test.ts` is untouched and
must stay green, which is the proof the prose path did not change.

#### D-27-W4-13 — Token steps pair with projection step rows 1:1 by step number; a mismatch falls back
`deriveProjectionTx` writes a `# Heading` row at every section boundary
(`cook-projection.ts:213-214`), so `steps[].order` and `cookTokens[].order` do **not**
line up. The pairing is therefore: the Nth **non-heading** native-system projection row
pairs with the Nth token step. Images (`steps[].images`) and any per-step UI state keep
coming from the projection row; prose, ingredients, timers and the section come from the
token step. If the two counts disagree, the recipe falls back to the legacy branch **in
full** — never a half-token render. This is the guard that makes a stale projection a
cosmetic degradation instead of a lost step.
