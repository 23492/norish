## Decisions taken FOR this wave (a later wave must not relitigate these blindly)

### D-27-W5P-01 — The dry-cup fix is a ONE-DIRECTIONAL, density-gated dimension preference
The measured defect (`2 cup flour` → `8.81849 ounce`) is **not** caused by a missing
unit ID. `fl oz` and `pint` are volume units; the failing conversion is `250 gram` →
US, which is mass → mass. Adding volume vocabulary cannot fix it. The mechanism that
does fix it is a **selection rule**:

> When `targetSystem === "us"` **and** the source dimension is `mass` **and**
> `findDensity(ingredient)` returns a real entry, the TARGET dimension becomes
> `volume`. In every other combination the target dimension equals the source
> dimension, exactly as today.

Properties that make this acceptable rather than a bandaid:
- **Deterministic.** Its only input is the density table. No text heuristic, no
  liquid/solid guess, no new data field.
- **Never fabricates.** No density entry ⇒ no crossing ⇒ the old mass ladder, so
  `chicken breast` still projects to `ounce`/`pound`.
- **One-directional.** Metric never crosses. `convertToSystem(1, "cup", "metric",
  { ingredient: "flour" })` still returns a volume, so W0's existing assertion at
  `convert-measure.test.ts:272` stays green **unedited**. Metric cooks weigh dry goods
  AND measure liquids by volume; a symmetric rule would need a liquid/solid
  classification we do not have and will not invent.
- **Matches the quality bar.** `250 gram flour` → `2 cup`, `100 gram sugar` →
  `0.5 cup`, `50 gram grated parmesan` → `0.5 cup` — each byte-identical to the AI row
  D-27-W3-07 recorded as better.

### D-27-W5P-02 — `fluid_ounce` and `pint` enter the VOCABULARY but NOT the automatic ladder
They become real canonical unit IDs (config entry, dimension, synonyms, valid explicit
`convertToUnit` target, round-trip) but `SYSTEM_TARGETS.volume.us` stays
`["cup", "tablespoon", "teaspoon"]`.

**Why — the evidence, not a preference.** The only quality bar this phase has is the
AI's US output measured in D-27-W3-07: across all 35 ingredients of 5 fixtures it used
`cup`, `tablespoon`, `teaspoon`, `pound` and `ounce` and **never once** `fl oz` or
`pint`. Every magnitude window either unit could occupy is a window where the ladder
already produces the unit a US recipe actually prints:
- `pint` = 2 cups exactly, so it can only displace `cup` at ≥ 4 cups — where "5 cups of
  stock" reads better than "2.5 pints of stock".
- `fl oz` = 1/8 cup = 2 tbsp, so its ONLY window is `[2 tbsp, 4 tbsp)`, where
  "3 tablespoons olive oil" reads better than "1.5 fl oz olive oil".

Putting either in the ladder would move the derived output AWAY from the measured bar.

**What the vocabulary addition buys instead, and it is not cosmetic:** today
`dimensionOf("fl oz")` and `dimensionOf("pint")` return `count`, so a US-authored
measure in those units is **system-neutral and returned unchanged — it never converts
at all**. An imported American recipe reading `14.5 fl oz` or `1 pint` currently gets
NO metric projection. After this wave it converts. That is the vocabulary gap, and it
is provable (see the vocabulary test).

**To reverse this decision** the director changes two lines: add the IDs to
`SYSTEM_TARGETS.volume.us` and give them `MIN_MAGNITUDE` entries. It is deliberately a
two-line change and is flagged in this plan's SUMMARY as a director decision point.

### D-27-W5P-03 — The rounding rule: 3 significant digits, never fewer than 0 decimals, at ONE site
`roundQuantity(v)`:
- `!Number.isFinite(v) || v === 0` ⇒ return `v` unchanged.
- `Math.abs(v) >= 1000` ⇒ `Math.round(v)` (integer). This branch exists because
  `Number((1234).toPrecision(3))` is `1230` — silently discarding a real integer digit.
- otherwise ⇒ `Number(v.toPrecision(3))`.

**Decimals, not fractions — and the justification is in the codebase, not in taste.**
`packages/shared/src/lib/format-amount.ts` already owns amount presentation and already
offers BOTH modes behind a per-user `AmountDisplayMode`: `formatAmountAsDecimal`
(`toFixed(2)`, trailing zeros stripped) and `formatAmountAsFraction` (fraction.js,
`simplify(0.01)`, denominator ≤ 16, Unicode glyphs). Rounding to a fraction inside the
converter would (a) fight a user who chose decimal mode and (b) round twice for a user
who chose fraction mode. The converter's job is to produce a **clean number**; choosing
how to draw it is `formatAmount`'s job and stays there.

**Why 3 significant digits.** It is one rule with no tiers to remember, its worst-case
relative error is 0.5% everywhere (at the bottom of a decade, e.g. `1.005` → `1.00`),
it restores integrality lost to floating point (`convert(2,'cup').to('fl oz')` is
`16.000000000000004` → `16`), and it never zeroes a positive value because the leading
significant digit is always preserved.

**Applied exactly once.** The only ok-result constructor is inside `convertToUnit`;
`convertToSystem` already returns `convertToUnit`'s result verbatim
(`convert-measure.ts:181-183`) and must keep doing so. There is one rounding site and
no second door.

### D-27-W5P-04 — `via: "identity"` is NOT presentation-rounded
An identity result means "this measure was not converted" — a `2 clove`, a
system-neutral `centimeter`, a same-unit passthrough. Re-rounding it would let the
converter silently rewrite a value nobody asked it to convert, which is the one thing
`27-ARCHITECTURE.md` forbids of the derive path. Identity keeps the existing 1e-6
determinism guard; `same-dimension` and `density` results get `roundQuantity`.

### D-27-W5P-05 — The units-config no-op trap is closed at the READ boundary, with no DB write
`syncUnits()` in `packages/api/src/startup/seed-config.ts` only migrates the WRAPPER
SHAPE — unlike `syncPrompts` / `syncTimerKeywords` it never compares the file contents
to the stored map. So on any install that already has a seeded `server_config.units`
row (which includes live) **adding a key to `units.default.json` is a silent no-op** —
structurally identical to the `loadPrompt` trap D-27-W3-01 already caught this fork on.

Two mechanisms were considered:
- a boot-time additive backfill in `syncUnits()` — rejected: it WRITES to
  `server_config` on deploy, which this wave's scope fence forbids, and an
  admin-customised map that was migrated to `isOverridden: false` by `syncUnits`'s own
  legacy branches would be at risk.
- a **read-time merge** — chosen. `resolveUnitsMap(storedValue)` returns
  `{ ...defaultUnits, ...stored }`: the stored value wins for every key it defines, and
  a key present only in the file falls through. No write, no migration, no boot
  mutation, fully reversible, and it fixes the whole class for every future unit.

**Stated tradeoff:** a unit an admin deliberately DELETED from the Admin-UI JSON would
reappear. Accepted — the units map is a recognition/formatting vocabulary, a
resurrected key is strictly additive (nothing that resolves today stops resolving), and
deleting a unit is not a workflow the Admin UI encourages.

The four-branch stored-value fallback is currently **duplicated verbatim** in
`getUnits` (`shared-server`) and `getUnitsForNormalization` (`db`). Both are replaced
by the single `resolveUnitsMap`, so the merge has one door, not two (the W3 lesson).

### D-27-W5P-06 — Generic `kaas` / `grated cheese` / `feta cheese` are NOT mapped
The wave brief asks for `kaas` → "the cheese entries". There is exactly ONE cheese
entry, `grated_parmesan` at 100 g/cup, and that figure describes **grated hard cheese**,
not cheese in general. Mapping bare `kaas`, `geraspte kaas`, `feta kaas` or
`mozzarella` onto it would attach a density to a food we have no figure for — precisely
what the UNITS decision in `27-DECISIONS.md` forbids ("Unknown-density ingredients are
flag-and-preserved, never fabricated") and what `ingredient-density.ts`'s own header
rule states ("a WRONG density match is worse than a flag").

What IS added is the Dutch name for the SAME food: `parmezaan`, `parmezaanse kaas`,
`geraspte parmezaan(se kaas)`. Everything else cheese-shaped stays uncovered and is
asserted to stay uncovered. **Surfaced to the director**: covering feta / mozzarella /
generic grated cheese needs three real USDA figures, which is a W5 table-expansion item,
not a rename.

### D-27-W5P-07 — `chopped_onion` is repaired, because it is currently DEAD
`PREP_DESCRIPTORS` strips `chopped` and `diced`, so `normalizeIngredientName("chopped
onion")` is `"onion"`, and both of the entry's aliases (`chopped onion`, `diced onion`)
are multi-word phrases that can never occur in that normalized string.
`findDensity("chopped onion")` returns `null` today. The entry is unreachable — a dead
row in a shipped table. The alias `onion` (and Dutch `ui`) is added, which makes it
reachable. This is not scope creep: the full-table alias-reachability invariant this
plan introduces FAILS until it is fixed, and shipping a table with a provably dead row
violates the fork's no-placeholders rule.
