<objective>
**Phase 27 — WAVE W5: migration `0042`, the live-data backfill.**

Every recipe that predates W3 still has `cook_source IS NULL` and renders through the
transitional legacy fork. This plan derives a `.cook` for each of them from its own
`steps` + `recipe_ingredients` rows, scores it, routes the low-confidence tail to
`cook_review_needed`, re-materializes the projection through `deriveProjectionTx`, and
runs the whole thing on live.

**Signed off by Kiran, 2026-07-27.** Two decisions are already made and are NOT to be
re-opened: (a) **no dry-run against a restored dump** — waived on the grounds that the
instance has no users; do not plan a rehearsal and do not gate the live run behind one;
(b) a fresh verified `pg_dump` taken immediately before the run is the **sole** recovery
path. Live footprint: **6 recipes, 136 ingredient rows, single household**.

**Output.** `0042` in the journal (live count 42 -> 43), a boot-time runner, and a live
run whose per-recipe outcome counts (derived-clean / low-confidence-flagged / refused)
are recorded as empirical assertions against the live DB.

**THE NEVER-BROKEN GUARANTEE FOR THIS WAVE.** A recipe either gains a clean, parsing
`.cook` or is left EXACTLY as it is. No shopping-list link is broken, no `steps.id`
moves, no ingredient row is lost, no household sees another's data, and a failure of any
kind costs a boot nothing — the app starts and serves the legacy path.

**FORWARD-ONLY, STATED PLAINLY.** `0042` mutates data. Rolling the image back does NOT
undo it: the previous image reads `cook_source` fine (it is nullable and W4's renderer
forks on it), but the rows the backfill rewrote stay rewritten. An incompatible data
effect is recovered only by restoring the pre-run dump.

**SCOPE FENCE.** `0043`, the `cook_source NOT NULL` tightening, the review-queue UI and
the repair tool are W6/later and are absent from this diff. No `steps` or
`recipe_ingredients` column is dropped. Native execution only.
</objective>

<decisions>
## Decisions taken FOR this wave — a later wave must not relitigate these blindly

### D-27-W5-01 — The backfill is a DETERMINISTIC seeder, not an AI re-linking pass
`27-ARCHITECTURE.md` §5 / D-6 name an AI re-linking pass with a deterministic name-match
seed as sanctioned migration glue. **This wave uses the seed and does not call the AI.**
Why: an AI pass is not reproducible, so "run it twice, get the same rows" — the
idempotency this plan must prove — is unachievable; it would put a provider call in the
boot path; and it is not needed to reach coverage, because the *placement inside a step*
is already done by the serializer's own anchoring, and the tail is carried by the
confidence gate plus the review queue that D-6 (amended) already requires. The seeder is
migration glue and is never reachable from a render path.

### D-27-W5-02 — `0042` is a journal migration; the mutation runs as `backfillCookSource()`
Minting a `.cook` requires `escapeCookText`, the serializer, the nine caps,
`findCookSourceDefect` and the pooled WASM parser. None of that is expressible in SQL,
and a SQL re-implementation would bypass exactly the injection surface T-27-01 closed —
which is the reason the rule "reuse the real code path" exists. `0042` therefore carries
the journal entry, asserts its own precondition (the `0041` natural-key unique index the
UPSERT depends on) and documents the mutation; `backfillCookSource()` performs it at
boot, immediately after `runMigrations()`, in the same idempotent-startup-step shape as
`migrateGalleryImages()`. The live migration count still advances 42 -> 43.

### D-27-W5-03 — THE CONFIDENCE SCORE AND THE REVIEW THRESHOLD (decided here, not at runtime)
`cook_confidence = inline_links / total_links`, rounded to 3 decimals (the column is
`numeric(4,3)`); `total_links === 0` scores `1.000`. `cook_review_needed` is set when the
score is **strictly below 0.800** (`COOK_REVIEW_CONFIDENCE_THRESHOLD = 0.8`).

*Why this is the only signal worth scoring.* §5 lists four signals. Three of them are
satisfied **by construction** under D-27-W5-01 and therefore carry no information: every
ingredient is referenced exactly once (no ingredient in >1 step), each carries its
structured amount verbatim (Σ per-step amounts == the structured total, always, because
nothing is split, summed or invented), and coverage is total (no orphans — see
D-27-W5-06). What genuinely varies is **placement**: `placement: "inline"` means the
token replaced the words the author actually wrote, so the step reads exactly as before
with a chip in it; `placement: "appended"` means the prose never names the ingredient, so
the token is appended — the amount is still right, the position is not. That is precisely
§8's accepted "best-effort" tail.

*Why 0.800.* One appended ingredient in five is the ordinary garnish / "season with salt"
case §8 names as accepted best-effort — it does not need a human. More than one in five
means the prose and the ingredient list have genuinely drifted apart, which is the state a
reviewer exists to repair. Comparison is strict `<`, so exactly 0.800 is NOT flagged;
`4/5 = 0.800` passes, `3/4 = 0.750` and `2/3 = 0.667` are flagged.

### D-27-W5-04 — The backfill writes ONLY the three cook columns
It does not touch `recipes.updated_at` or `recipes.version` and emits **no realtime
event**. The recipe's user-visible content did not change — a `.cook` derived from the
recipe's own rows is derived metadata — so `updated_at` must keep meaning "last user
edit" (it orders the user's list), and a boot-time emit would be a new emit site with a
new policy surface for no gain.

### D-27-W5-05 — `cook_review_needed` is STICKY, and the OR must happen in SQL
`0041`'s lossy-merge branch may already have set it. `getRecipeFull` does **not** select
`cook_confidence` / `cook_review_needed` (the DTO defaults them to `null` / `false`), so
reading the flag through the DTO and writing it back would silently CLEAR a real one. The
write is therefore `cook_review_needed = cook_review_needed OR $flag` in the UPDATE
statement. It is never cleared by this wave.

### D-27-W5-06 — The grocery-link guard: coverage is total, and an abort is the fallback
Two mechanisms keep `deriveProjectionTx`'s retirement delete from taking a row the
shopping list points at. First, **coverage is total by construction**: every native-system
`recipe_ingredients` row becomes a ref on some step (unanchored ones are appended to the
first non-heading step), so the derived row set is a superset of the ingredient ids that
exist today. Second, because the *opposite* system's live rows may reference ingredient
ids the native system does not (the pre-W3 AI converter could name them differently), the
writer **snapshots every `recipe_ingredients.id` a `groceries` row points at before
deriving and re-checks them after**; if any is gone it throws `GroceryLinkWouldBreakError`
and the recipe's whole transaction rolls back — no `cook_source`, nothing changed, counted
as `refused`. Never null a household's "from recipe X" link to make a migration succeed.

### D-27-W5-07 — W3's deferred item SETTLED: KEEP dual-system extraction
D-27-W3-07 deferred single-system extraction because the derived US projection was worse
than the AI's on **18 of 35 ingredients** on two axes. W5-PREP (plan 27-06) closed both
named prerequisites — the `kilogram`/`fluid_ounce`/`pint` vocabulary and `roundQuantity` —
and both are live. **Dual-system extraction is nevertheless KEPT, and this decision is
deliberate, not inertia:**

1. Only the *flagship row* was re-measured (`250 g flour` -> `2 cup`). The 35-ingredient
   comparison that produced the verdict has not been re-run, so there is no evidence the
   remaining 17 differences closed.
2. Two known gaps survive W5-PREP by explicit decision: D-27-W5P-02 keeps `fluid_ounce`
   and `pint` out of the automatic US ladder, and D-27-W5P-06 leaves 14 of the 25 measured
   Dutch names with no density at all — so on live-shaped data the derived side is still
   known-incomplete.
3. The asymmetry is decisive: keeping dual extraction costs nothing (it is the shipped
   behaviour), while switching is **irreversible for every recipe imported under it** —
   there is no second authored system to fall back to.

**Entry condition for reversing this, recorded so it is cheap:** re-run the D-27-W3-07
measurement that already lives in
`packages/api/__tests__/ai/features/recipe-extraction/cook-payload.test.ts` and get either
0 differences across the 35 ingredients or a difference set the director explicitly
accepts. Task 2 records the current number in the SUMMARY. Even if it is 0, the switch is
NOT made here — it is an extraction-path change, out of this plan's scope, and belongs to
the director with the evidence in hand.

<risks>
**R1 — The opposite system's live rows may use different ingredient ids.** Pre-W3 rows for
the non-native system were produced by the AI converter and may carry ingredient ids the
native list does not. `deriveProjectionTx` retires any row for an ingredient the `.cook`
does not mention, which would delete those rows and null a grocery FK pointing at one.
*Mitigation:* D-27-W5-06's guard aborts that recipe. *Expected on live:* the pre-run
postcheck reports whether any grocery row points at an opposite-system row at all.

**R2 — Appended tokens are user-visible.** W4's renderer is live, so a backfilled recipe
switches from the legacy fork to the token renderer immediately. An unanchored ingredient
appears as a chip at the end of the first step. This is §8's accepted best-effort tail,
flagged when it is common enough to matter (D-27-W5-03), and it is why the live task
includes opening a backfilled recipe in cooking mode.

**R3 — The step projection rewrites step prose.** `computeCookProjection` rebuilds each
`steps.step` from the token list, so the stored prose round-trips through
escape -> parse -> `stepProse`. W3's 45-test fidelity suite proves that is byte-identical
except for two documented normalizations (CR/LF in prose folds to a space; an unpaired
UTF-16 surrogate becomes U+FFFD). *Mitigation:* Task 2 asserts the round-trip on a hostile
fixture; the live postcheck compares step counts per recipe.

**R4 — A boot-time job that throws blocks the deploy.** *Mitigation:* the runner catches
per recipe AND at the top level; it never rethrows. A backfill failure must never cost a
boot.

**R5 — Stale `node_modules/@norish/*` hardlink farms** (W2/W3 standing finding). New files
in `@norish/db` / `@norish/api` may be invisible to another package until re-synced.
*Mitigation:* the executor re-syncs after creating a new module and never `cat`/`cp`
between a workspace file and its `node_modules` copy in the same direction.
</risks>
