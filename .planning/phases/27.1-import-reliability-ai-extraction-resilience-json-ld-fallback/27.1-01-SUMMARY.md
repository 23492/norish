# Phase 27.1 Plan 01: AI extraction resilience — mirror, relax, retry Summary

**Metric-only (or US-only) AI extractions now import via a pure `mirrorMeasurementSystems` mirror + a relaxed `validateExtractionOutput`, and a transient AI extraction failure gets exactly one retry with a measured, product-decided 100k-token headroom — closing all three sub-causes of the intermittent `AI extraction failed` import bug.**

## Performance

- **Duration:** ~50 min (not precisely timestamped at start; estimated from session activity)
- **Completed:** 2026-07-28T07:46:42Z
- **Tasks:** 2 / 2 completed
- **Files modified:** 6 (5 source, 1 pre-existing test file updated) + 2 new test files created

## Accomplishments

- A complete metric-only (or US-only) AI extraction now imports: `mirrorMeasurementSystems` copies the populated measurement system's array onto the empty side, independently for `recipeIngredient` and `recipeInstructions`, before validation — the real logged failure shape (`metricIngredients: 10, usIngredients: 0`) is proven `valid: true` both before and after mirroring.
- `validateExtractionOutput`'s required-fields check is `name` + `recipeIngredient.metric.length` + `recipeInstructions.metric.length` only; the two `us`-required clauses are gone. `details.us*` remains for observability. Genuinely empty/nameless/zero-metric extractions still reject with the byte-identical error strings (`"AI returned empty response"` / `"Recipe extraction failed - missing required fields"`).
- All three AI extraction call sites (`recipe-parser.ts`, `image-recipe-parser.ts`, `video/normalizer.ts`) apply the mirror exactly once, immediately after `generateText`, so validate/normalize/`buildCookFromExtraction` all read one mirrored object — `buildCookFromExtraction` can no longer silently read an empty `output.recipeInstructions[systemUsed]` when the model omitted that half.
- `tryExtractWithAI` in `packages/api/src/parser/index.ts` makes at most two attempts. A first failure retries exactly once when `result.code` is in the closed `RETRYABLE_AI_EXTRACTION_CODES` set (`PROVIDER_ERROR, EMPTY_RESPONSE, TIMEOUT, NETWORK_ERROR, RATE_LIMIT, VALIDATION_ERROR, UNKNOWN`); `AI_DISABLED`, `AUTH_ERROR`, `INVALID_INPUT` never retry.
- The retry — and only the retry — asks `extractRecipeWithAI` for `outputTokenFloor: AI_RETRY_OUTPUT_TOKEN_FLOOR` (100 000), which the callee applies as `Math.max(configuredValue ?? 0, floor)`, never lowering a configured value and never touching the first attempt.
- `AI_RETRY_OUTPUT_TOKEN_FLOOR = Math.min(AI_RETRY_OUTPUT_TOKEN_TARGET, AI_PROVIDER_MAX_OUTPUT_TOKENS)` resolves to exactly `100_000`, proven by a dedicated test asserting the equality against the live constants (so a future ceiling drop below 100 000 fails loudly instead of silently shrinking the retry).

## Decisions Made

- Mirroring beats rejecting a complete single-system extraction (D-27.1-03) — no other validation is weakened; only the two `us`-length clauses are removed.
- The retry lives inside `tryExtractWithAI` rather than at the `useAIOnly` throw site, because this one edit covers both the `useAIOnly` branch and the structured-failure AI fallback, and doesn't re-run the JSON-LD-input attempt an outer wrap would.
- `AI_RETRY_OUTPUT_TOKEN_TARGET = 100_000` per Kiran's explicit 2026-07-28 product decision (superseding the plan's original 32 000); `AI_PROVIDER_MAX_OUTPUT_TOKENS = 393_216` is a measured DeepSeek fact (393_217 → HTTP 400), so the clamp is dead code today and written for the next provider swap.
- `packages/shared-server/src/config/defaults.ts` intentionally untouched — confirmed inert on live (D-27.1-06/F-2).
