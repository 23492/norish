# Phase 27.1 Plan 02: JSON-LD fallback — AI stays primary, JSON-LD rescues a total AI failure Summary

**A page shipping valid schema.org Recipe JSON-LD now survives a total AI extraction failure via an explicit `tryJsonLdFallback`, which reuses W5's deterministic seeder to mint a real `cook_source` through the sole sanctioned minter whenever the linkage scores ≥ 0.800 — degrading to exactly today's `cook_source` NULL behaviour below that gate, with every terminal parse path now greppable via one `parserPath` marker per import.**

## Accomplishments

- **`tryJsonLdFallback`** (`packages/api/src/parser/jsonld-fallback.ts`) turns a JSON-LD-bearing page into a full `FullRecipeInsertDTO` plus, when the deterministic linkage earns it, a cleanly-parsing `.cook` — extracting via the existing `tryExtractRecipeFromJsonLd`, seeding via `buildStructuredRecipeFromLegacy`, scoring via `cookConfidenceFromLinks`, and minting ONLY through `buildCookPayload` (the escaping, the nine caps, `findCookSourceDefect`, the pooled bounded parser). The whole body runs inside one try/catch and NEVER throws — a failing extractor, seeder, or minter degrades to `null` (no fallback available) or `{ recipe, cook: null }` (fallback available, no `.cook` earned), never costing the user their import.
- **`buildStructuredRecipeFromLegacy` widened, not forked**, to a locally-declared, exported structural `LegacyProjectionSource` type. Both `FullRecipeDTO` (W5's original read-DTO caller) and `FullRecipeInsertDTO` (this plan's insert-DTO caller) satisfy it. The function now: coerces `order` with `Number(...)` (the insert DTO's `order` z.INPUT type is `unknown`, since `z.coerce.number()` widens its own input type); skips any ingredient whose trimmed `ingredientName` is empty rather than crashing or linking an empty name; treats a missing per-row `systemUsed` as the recipe's own native system; and defaults a missing recipe-level `systemUsed` to `"metric"` and missing `steps`/`recipeIngredients` arrays to `[]` (both discovered via `tsc`, not anticipated by the plan's sketch — see Deviations). Every existing assertion in `backfill-cook-source.test.ts` (28 tests) passes unchanged; 5 new tests prove the widening.
- **`parseRecipeFromUrl` wired at BOTH AI-failure exits, and only there**: the `useAIOnly` throw site, and the final fall-through past the non-`useAIOnly` AI fallback attempt. AI STAYS PRIMARY — proven by tests asserting the fallback spy is called `0` times whenever any AI attempt succeeds, and by the `useAIOnly`/non-`useAIOnly` control flow itself, which structurally guarantees at most one of the two exits is ever reached per invocation. A page with no JSON-LD at all still hits the unchanged `"AI extraction failed"` / `structured.failure.message` / `"Cannot parse recipe."` throws, byte-identical to today.
- **Every terminal outcome logs exactly one `"Recipe import: parse path taken"` marker** carrying `parserPath` (`"ai"` | `"jsonld-fallback"` | `"structured"`), `usedAI`, `cookMinted`, and `jsonLdNodeCount` (computed once, right after fetch succeeds, via `extractRecipeNodesFromJsonLd(html).length`). `usedAI: false` on a fallback result is preserved end to end, so `packages/queue/src/recipe-import/worker.ts` still enqueues auto-tagging, allergy detection, and auto-categorization for a fallback-sourced recipe exactly as it would for a python-scraper import.
- **Finding F-4 fixed**: `packages/api/src/parser/fetch.ts`'s stale comment (claiming a non-existent plain-HTTP fallback) rewritten to describe the real contract — comment-only, verified against `camofox.ts`, zero behaviour change.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `LegacyProjectionSource`'s sketch in the plan did not account for three more z.input widenings on `FullRecipeInsertDTO`**
- **Found during:** Task 1, first `tsc --noEmit` after writing `jsonld-fallback.ts`
- **Issue:** The plan's `LegacyProjectionSource` interface declared `systemUsed: MeasurementSystem` (required), `steps`/`recipeIngredients` as required arrays, and ingredient `order`/`amount` as `number | string` / `number | null`. Against the REAL `FullRecipeInsertDTO` (`z.input<FullRecipeInsertSchema>`), all of these are actually optional or `unknown`: `recipes.system_used` has a DB default, so drizzle-zod's insert schema makes recipe-level `systemUsed` optional; `steps`/`recipeIngredients` both carry `.default([])`, making them optional too; and `z.coerce.number()`'s own `z.input` type is `unknown` (not `number | string`), so both `order` and `amount` widen to `unknown` at the insert-DTO level. `tsc` failed to compile `tryJsonLdFallback`'s call to `buildStructuredRecipeFromLegacy(recipe)` on each of these in turn.
- **Fix:** Widened `LegacyProjectionSource`'s four fields (`systemUsed`, `steps`, `recipeIngredients`, and `order`/`amount` inside the array element types) to match the REAL z.input shapes, with explicit runtime defaulting inside the function (`recipe.systemUsed ?? "metric"`, `recipe.steps ?? []`, `recipe.recipeIngredients ?? []`, `Number(order)`, and a documented cast for `amount` at the point `StructuredIngredientRef` is built). Every default chosen matches the column's own DB default or the schema's own `.default(...)`, so no new behavior was invented — only the type was corrected to match reality.
- **Files modified:** `packages/api/src/startup/backfill-cook-source.ts`
- **Verification:** `pnpm exec tsc --noEmit` (api) clean; all 33 pre-existing + 5 new `backfill-cook-source.test.ts` assertions pass unchanged.
- **Committed in:** `5ef6ebaa` (Task 1 commit)
