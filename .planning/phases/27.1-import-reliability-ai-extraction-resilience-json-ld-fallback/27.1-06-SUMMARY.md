## Decisions Made

- **`everyone` gets no branch of its own.** Per D-27.1-12 and AGENTS.md's "a reachable `everyone` branch is the foot-gun" rule, the fix removes the branch rather than special-casing it — `everyone` and `household` share one clamp; only `owner` is narrower and split out.
- **No server-admin exemption.** The pre-existing `household`/`owner` branches had none; adding one inside a security fix would be a new widening invented by the fix, not a defect it corrects. `config.tags` and `buildViewPolicyCondition` DO exempt admins — that divergence is deliberate and stated in the code comment, because `getPending` hydrates a dashboard skeleton, not an admin surface.
- **F-5 deliberately deferred.** The four `is*` id-probes (`isNutritionEstimating`, `isAutoTagging`, `isAutoCategorizing`, `isAllergyDetecting`) apply no ownership check at all, but the response is a boolean about an id the caller must already possess, not a recipe or url — materially lower severity than F-1, and both sources that used to hand out arbitrary cookbook recipe ids are now closed. Raised for separate scheduling, not fixed here (plan scope was locked at one defect by the director).

**None — plan executed exactly as written**, with one clarification made during test authoring (see below), which is a test-correctness fix rather than a scope or behavior deviation:

**1. [Rule 1 - Test bug, fixed before RED capture] Corrected an assertion in the cross-household test for `JOB_A_IN_B`.**
- **Found during:** Task 1, while first drafting the isolation suite (before the RED capture used as evidence below).
- **Issue:** The test originally asserted that cookbook B's caller must never see `JOB_A_IN_B` (a job owned by user-a but queued INTO cookbook B's household) under `household`/`everyone` view. That assertion was wrong: the household-level clamp legitimately matches on `householdKey` alone, and `JOB_A_IN_B`'s `householdKey` is `"cookbook-b"` — so cookbook B's own household view correctly includes it. Only the narrower `owner` level distinguishes by who queued the job.
- **Fix:** Split the assertion so `owner` expects `[URL_B]` only, while `household`/`everyone` expect `arrayContaining([URL_B, URL_A_IN_B])` — matching the actual, correct clamp semantics rather than an incorrect assumption about household boundaries.
- **Files modified:** `packages/trpc/__tests__/recipes/pending-isolation.test.ts` (this was corrected before the file was ever run, so it does not appear in the RED output below, which reflects the corrected assertions).
- **Verification:** Confirmed the corrected assertion passes under `household`/`owner` (both already correct pre-fix) and only `everyone` fails pre-fix, exactly matching the intended defect.

**Total deviations:** 1 (test-authoring correction, not a behavior or scope change). **Impact on plan:** none — the production fix and its scope are exactly as specified in the plan.

## Finding F-5 (raised, not fixed — for the director to schedule separately)

**The four unchecked `is*` job probes apply no ownership check at all.**

- `isNutritionEstimating` — `packages/trpc/src/routers/recipes/pending.ts:58-74`
- `isAutoTagging` — `packages/trpc/src/routers/recipes/pending.ts:102-118`
- `isAutoCategorizing` — `packages/trpc/src/routers/recipes/pending.ts:120-136`
- `isAllergyDetecting` — `packages/trpc/src/routers/recipes/pending.ts:166-182`

Each answers `jobs.some(job => job.data.recipeId === input.recipeId)` with **no ownership or cookbook check whatsoever**, so any authenticated caller can ask whether an ARBITRARY recipe id currently has a queued job. This is the "Authenticating is not authorizing" pattern AGENTS.md names.

**Severity reasoning (materially lower than F-1/PENDING-ISO-01):** the response is a boolean about an id the caller must already possess — not a recipe, not a url, not an enumerable list. Both sources that used to hand out other cookbooks' recipe ids for free — `getPending` (fixed by this plan) and the pre-D-22-01 socket broadcast (fixed in Phase 22, REALTIME-ISO-01) — are now closed. An attacker would need to already have a recipe id from some other leak to get any signal from these four probes.

**Deliberately not fixed here.** The director's override (D-27.1-12) scoped this plan at exactly one defect (PENDING-ISO-01); F-5 needs its own scheduling decision. No test was added asserting the (currently unguarded) behavior — per the plan's explicit instruction, only documentation.
