## Decisions (LOCKED — non-negotiable)

### D-27.1-01 — The root cause is INTERMITTENT, with three sub-causes. Do not re-derive it.

Six `AI extraction failed` events over ~72 h, interleaved with SUCCESSES on the very same URLs.

1. **The strict validator discards good recipes.** `validateExtractionOutput`
   (`packages/api/src/ai/features/recipe-extraction/normalizer.ts:180-191` — verified) hard-rejects
   when `!output.recipeIngredient?.us?.length`. A real logged failure carried
   `metricIngredients: 10, usIngredients: 0` — a complete, correct metric recipe thrown away as
   `Recipe extraction failed - missing required fields` / `VALIDATION_ERROR`.
2. **Reasoning-token exhaustion.** DeepSeek spends heavy reasoning tokens (470 on a 104-token
   prompt); on large HTML this can exhaust the output budget, yielding empty content →
   `NoOutputGeneratedError` → `PROVIDER_ERROR`.
3. **No retry.** `packages/api/src/parser/index.ts:245` (`throw new Error("AI extraction failed")`,
   inside the `useAIOnly` branch opened at `:242`) throws on the FIRST AI failure.

### D-27.1-02 — RULED OUT. Do not plan work against any of these.

- **The DB cleanup of broken recipes.** Schema intact, 0 orphaned FKs, migrations 43/43, both users
  have a valid `active_household_id`. No import precondition requires a pre-existing recipe row.
- **The 27-07 / W5 Cooklang work.** `StepWouldBeLostError` is reachable only from
  `backfillCookSource` (`packages/db/src/repositories/cook-backfill.ts`), never from
  `createRecipeWithRefs`. `backfillCookSource` cannot throw and is additionally try/caught at
  `apps/web/server/index.ts:38-45`.
- **DeepSeek lacking structured output — REFUTED.**
  `node_modules/@ai-sdk/deepseek/dist/index.mjs:472` hardcodes `response_format {type:"json_object"}`;
  a direct curl with the live key returned valid recipe JSON, `finish_reason "stop"`, usage
  `prompt_tokens 104 / completion_tokens 561 / reasoning_tokens 470`. The logged
  `responseFormat JSON schema is used in a compatibility mode` warning is BENIGN, not causal.

### D-27.1-03 — Normalizer relaxes to `name` + `recipeIngredient.metric` + `recipeInstructions.metric`; the absent half is MIRRORED, never a rejection.

No other validation is weakened. Mirroring is symmetric (a US-only extraction mirrors us → metric),
so the relaxed rule holds for either single-system shape. Unit tests must cover: metric-only input
succeeds and yields a mirrored `us` half; genuinely empty / nameless input still rejects.

### D-27.1-04 — AI STAYS PRIMARY. JSON-LD is a FALLBACK, never a bypass.

Cooklang `cook_source` quality and bilingual metric/US output both come from the AI extraction's
per-step linkage (D-27-W3-03). JSON-LD is reached ONLY after AI extraction has FINALLY failed, so a
page shipping valid schema.org Recipe never hard-fails. `tryExtractRecipeFromJsonLd`
(`packages/api/src/parser/legacy.ts:14` → `packages/api/src/parser/jsonld.ts:122`) already exists but
is reachable only behind `LEGACY_RECIPE_PARSER_ROLLBACK`, which is UNSET in the container. Today
JSON-LD is used only as cheaper AI *input* (`packages/api/src/parser/index.ts:108-124`).
**The `LEGACY_RECIPE_PARSER_ROLLBACK` flag semantics are NOT resurrected** — the fallback is wired
explicitly.

### D-27.1-05 — The JSON-LD fallback mints its `.cook` through the SANCTIONED minter, reusing W5's deterministic seeder and its confidence gate. *(Extends Phase 27 D-6 — flagged for director acknowledgement.)*

A JSON-LD-sourced recipe must flow through the same normalizer → `createRecipeWithRefs` → cook
projection path as any other import. The mechanism is the one W5 already shipped and proved:
`buildStructuredRecipeFromLegacy` + `cookConfidenceFromLinks` + `COOK_REVIEW_CONFIDENCE_THRESHOLD`
(`packages/api/src/startup/backfill-cook-source.ts`) → `buildCookPayload` (the only sanctioned
minter). Below the 0.800 threshold no `cook` argument is passed, so the recipe keeps the legacy
projection with `cook_source` NULL — **byte-identical to what every python-scraper import does on
live today**, therefore no regression.

**The tension, stated rather than buried.** Phase 27's D-6 permits a deterministic name-match seed
"as *migration glue*, never as a runtime renderer", and `parser/index.ts:252` records D-27-W3-08 as
"the structured paths produce NO linkage, so no `.cook`". This decision extends D-6 by running that
same seeder on a runtime import path. It does **not** breach D-7: no heuristic *renderer* is
introduced, `SmartInstruction` / `applyIngredientLinkMarkup` / `createIngredientLinkCandidates` stay
deleted, and the stored `.cook` is rendered by the parser-token renderer like any other. It is also
forward-necessary: **W6 makes `cook_source` NOT NULL**, at which point a non-AI import path that
produces NULL becomes a hard failure — this makes the fallback W6-ready instead of adding debt.

### D-27.1-06 — Token headroom: raising the `defaults.ts` value is INERT on live. The fix is a headroom-raised RETRY, not a new floor.

`getGenerationSettings()` (`packages/shared-server/src/ai/providers/factory.ts:215-223`) reads
`maxOutputTokens` from `getAIConfig(true)` — the **DB `ai_config` row**, not
`packages/shared-server/src/config/defaults.ts:33`. Live has held a configured `ai_config` since
2026-06-15, so editing the default changes nothing on live. A hard per-task floor was considered and
REJECTED: `maxTokens` is admin-configurable across providers whose output caps differ (some Groq
models cap at ~8 k), so an unconditional floor could break a working configuration.

**Decision:** ONE retry on transient AI failures, and the retry — and only the retry — runs with
raised output headroom. This addresses sub-causes 2 and 3 with a single mechanism, cannot regress a
healthy configuration (the first attempt already failed when it runs), and needs no config change.
`defaults.ts` is left alone; see Finding F-2.

### D-27.1-07 — The failed-emit path becomes UNCONDITIONAL, and failure renders as a real error state.

`handleJobFailed` (`packages/queue/src/recipe-import/worker.ts:208-246`) runs unguarded work —
`deleteRecipeImagesDir(recipeId)` at `:231` and `resolveHouseholdRealtimeScope` at `:235` — BEFORE
the `failed` emit at `:240`. A throw in either is only logged
(`packages/queue/src/lazy-worker-manager.ts:259-263`), leaving an eternal skeleton card. Guard the
pre-emit work so nothing can swallow the event.

Client-side, `onFailed` today only shows a toast and drops the skeleton
(`packages/shared-react/src/hooks/recipes/dashboard/use-recipes-subscription.ts:207-223`). A toast is
missable; the phase requires a **rendered** error state in the grid, in place of the skeleton,
dismissible by the user.

Constraints carried forward: the phase-24 `importProgress` / `RecipeImportStage` contract
(`packages/shared/src/contracts/dto/queue.ts:18`), and the phase-22 realtime rules — `emitByPolicy`
must NOT broadcast, and the scope comes from the recipe's own cookbook (here, the import's target
cookbook via `resolveHouseholdRealtimeScope`). Any new user-facing string lands in ALL 12 locales
(`pl, de-formal, de-informal, it, en, ru, ko, nl, fr, da, es, no`) and `pnpm i18n:check` must pass.

### D-27.1-08 — Camoufox: the REPO is already correct; the gap is the untracked live compose. No live mutation in this phase.

Verified during planning:
- `packages/config/src/env-config-server.ts:249-252` — `CAMOFOX_URL` already defaults to
  `http://camofox:9377`, the in-stack service name.
- `docker/docker-compose.example.yml:139-159` — already defines a `camofox` service built from the
  vendored `docker/camofox` source, with `depends_on: camofox` on the app (`:123`) and
  `CAMOFOX_URL: http://camofox:9377` (`:18`).

The defect is that the LIVE stack file `/opt/norish/docker-compose.fork.yml` is **outside the repo
tree**, defines only `norish`/`db`/`redis`, and only works because `CAMOFOX_URL` points off-stack at
LXC 105 (`norishp2-camofox-1` on network `norishp2_default`, unreachable from `norish_default`) — an
undocumented single point of failure. The Camoufox service itself is HEALTHY: a full
open/act/evaluate/close probe against `http://192.168.2.26:9377` returned 200s and rendered a real
recipe page (`hasRecipeLd: true`). This is an **architecture/config fix, not a repair**.

**Deliverable:** a repo-tracked `docker/docker-compose.fork.yml` that mirrors the live stack and adds
the in-stack `camofox` service, plus an operator runbook. `CAMOFOX_URL` stays an explicit override.
**No task may mutate the live stack** — live cutover is a separate, deliberate step owned by the
deploy agent (CLAUDE.md: "the live stack is untouched mid-phase").

### D-27.1-09 — The post-deploy empirical gate is its OWN plan, non-skippable, and runs AFTER the image is built and deployed.

Requested by the director directly. Driven through the existing authenticated REST surface
`POST /api/v1/recipes/import/url` (`packages/trpc/src/routers/recipes/recipes.ts:423-463`,
`x-api-key` header per `packages/auth/src/auth.ts:623`), so the gate is scriptable rather than a
vague "test it". Bars, in order:

1. `https://www.ah.nl/allerhande/recept/R-R951540/bonensalade-met-kip-en-avocado` imports successfully.
2. Then **≥ 10 FURTHER** ah.nl/allerhande recipes across **≥ 6 distinct categories** (bakken/dessert,
   soep, vegetarisch, pasta, vlees, vis, salade, ontbijt) import successfully.
3. **ONLY once bar 2 passes**, **≥ 5** recipes from `https://www.lekkerensimpel.com/`.
   *(The ≥ 5 figure is the planner's measurable reading of an unspecified "as well"; the director may
   revise it.)*

Per URL, record: fetch OK, JSON-LD present, **which path was taken (AI vs JSON-LD fallback)**,
ingredient counts metric/us, whether `cook_source` derived, and any failure mode VERBATIM. A failure
must present as a VISIBLE error, never an eternal skeleton.

## Findings raised during planning — NOT in this phase's scope

**F-1 — `getPending` leaks pending imports across cookbooks under the LIVE policy. (Security; live today.)**
`packages/trpc/src/routers/recipes/pending.ts:29-32` returns `true` for **every** queued job when
`policy.view === "everyone"`, which is the live server-wide value. Every authenticated user is
therefore served every household's pending imports, `recipeId` **and** source `url` included. This is
the fourth member of the family `AGENTS.md` documents (REALTIME-ISO-01, IMPORT-DEDUP-ISO-01,
LIST-ISO-01): a code path reading `everyone` as *unscoped* instead of clamping it to the cookbook.
It is **pre-existing and independent of this phase** — the new `failed` event goes through
`emitByPolicy`, which clamps `everyone` at the cookbook boundary, so nothing 27.1 adds widens it.
Deliberately NOT planned here (the phase scope is locked at five items). Proposed id
**PENDING-ISO-01**; raised to the director for a scheduling decision.

**F-2 — `defaults.ts` AI budget is tight for reasoning models on new installs.**
`packages/shared-server/src/config/defaults.ts:33` still defaults `maxTokens: 10000`. Inert for live
(D-27.1-06) and therefore deliberately not changed here, but a fresh fork install pointed at a
reasoning model starts on the same tight budget. The retry-with-headroom mechanism covers it at
runtime regardless of config; a default bump is a separate, provider-cap-aware decision.

**F-3 — `docker/docker-compose.beta.yml:38` mirrors the live SPOF into the repo.**
`CAMOFOX_URL: ${CAMOFOX_URL:-http://192.168.2.26:9377}` hardcodes the off-stack LXC-105 address as
the beta stack's default. Corrected as part of 27.1-04, which is already in that file's neighbourhood.

**F-4 — `packages/api/src/parser/fetch.ts:8-10` documents a fallback that does not exist.**
The comment claims the function "Returns an empty string on failure so callers can fall back to a
plain HTTP fetch." There is no plain-HTTP fallback anywhere; `parseRecipeFromUrl` throws
`Cannot fetch recipe page.` Corrected in 27.1-02, which edits that file's caller.
