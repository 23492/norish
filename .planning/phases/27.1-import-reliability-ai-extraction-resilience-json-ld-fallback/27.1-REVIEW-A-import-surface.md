## Critical

### CR-01: `typecheck` is a no-op in both TS packages; the cross-package contract is unenforced

**File:** `packages/api/package.json:15`, `packages/queue/package.json:17`
**Also:** `packages/api/package.json:12`, `packages/queue/package.json:14` (same flag on `build`)

```json
"typecheck": "pnpm exec tsc --noEmit --noCheck",
```

`--noCheck` disables **all** type checking; combined with `--noEmit` the command does literally
nothing but parse. `pnpm typecheck` has therefore never typechecked the recipe parser, the AI
extraction path, the Camoufox client, or any queue worker.

**Why it matters here specifically.** `packages/queue/src/api-handlers.ts:9-19` documents:

> "the registration in `packages/api/src/startup/register-queue-api-handlers.ts` is checked against
> this interface"

That is the *only* thing preventing `QueueParseRecipeResult` (`api-handlers.ts:26-31`) from drifting
away from `ParseRecipeResult` (`packages/api/src/parser/index.ts:30-52`), and the *only* thing
checking the 18 hand-registered handlers at `register-queue-api-handlers.ts:24-43`. That check is
performed by `tsc` — which is switched off. The stated mitigation does not run.

The contract has **already** drifted: `QueueApiHandlers.extractRecipeWithAI`
(`api-handlers.ts:61-67`) declares five parameters; the real `extractRecipeWithAI`
(`packages/api/src/ai/recipe-parser.ts:56-63`) gained a sixth (`options?:
ExtractRecipeWithAIOptions`) in 27.1-06. Structurally assignable today, so harmless — but it is
proof that nothing is watching.

**Additionally:** `packages/api/tsconfig.json` and `packages/queue/tsconfig.json` both set
`"include": ["src"]`. The `__tests__/` trees are excluded from the compilation unit entirely, so
even removing `--noCheck` would leave every test file untypechecked.

**Verification:** I ran the real check and both packages are currently clean —
```
cd packages/api  && tsc --noEmit -p tsconfig.json   # exit 0, no output
cd packages/queue && tsc --noEmit -p tsconfig.json   # exit 0, no output
```
So this is a **gate defect, not a latent type error**: the fix is cheap and safe today, and every
day it is deferred the fix gets more expensive.

**Compare:** `packages/db`, `packages/shared`, `packages/config`, `packages/i18n`, `packages/ui`,
`packages/db-schema`, `packages/shared-react`, `apps/web`, `apps/mobile` all run a real
`tsc --noEmit`. Only `api`, `queue`, `auth`, `shared-server` and `trpc` use `--noCheck`.

**Fix:**
```jsonc
// packages/api/package.json, packages/queue/package.json
"typecheck": "pnpm exec tsc --noEmit",
```
and add the test tree to the typecheck scope (separate `tsconfig.test.json` extending the package
config with `"include": ["src", "__tests__"]`, `"noEmit": true`) so the mocks and the modules they
mock are checked against each other. Keep `--noCheck` on `build` only if the emit-declarations-only
path genuinely needs it.

### CR-02: `"AI extraction failed; attempting the JSON-LD fallback"` fires when AI was never invoked

**File:** `packages/api/src/parser/index.ts:345-361` (the logger), called from `:454-459`

```ts
async function finishWithJsonLdFallback(url, html, recipeId, reason) {
  log.warn(
    { url, reason, parserPath: "jsonld-fallback" },
    "AI extraction failed; attempting the JSON-LD fallback"   // :353 — unconditional
  );
```

**Control flow that produces the false message** (non-`useAIOnly` path):

| line | step |
|---|---|
| `:418` | `tryStructuredParser` → python scraper → fails (`NoSchemaFoundInWildMode` on a blogspot page) |
| `:421` | `structured.recipe` is null → fall through |
| `:430` | `const aiEnabled = await isAIEnabled()` |
| `:432` | `if (aiEnabled && (await isPageLikelyRecipe(html)))` — **if either is false the whole AI block at `:432-452` is skipped** |
| `:454` | `finishWithJsonLdFallback(...)` is called **unconditionally**, and `:353` asserts AI failed |

`isPageLikelyRecipe` (`:485-495`) requires a schema.org indicator **or** ≥2 content indicators. A
blogspot recipe page written in Dutch with no JSON-LD trips neither, so `:432` short-circuits, AI is
never called, and the warning fires anyway. That is exactly the observed live signature: **6
`"AI extraction failed; attempting the JSON-LD fallback"` lines, 0 `"Attempting AI extraction"`
lines** (`:175`) — 2 imports × 3 BullMQ attempts.

**The `reason` field lies too.** The default at `:458` is `"structured-and-ai-failed"`. When
`structured.failure` is null *and* AI was skipped, the log claims both failed when neither AI ran.

**Contrast:** the `useAIOnly` call site (`:398`) passes `"ai-only-extraction-failed"` and is
correct — that branch always runs AI first (`:387`). The defect is confined to the `:454` call site.

**Cost:** at a 7% live AI success rate (27 attempts / 2 completions), the operator reading these
logs concludes the AI provider is failing. It may not have been asked.

**Fix:** make the message reflect what actually happened, and stop asserting a step that may have
been skipped.
```ts
async function finishWithJsonLdFallback(
  url: string,
  html: string,
  recipeId: string,
  reason: string,
  aiAttempted: boolean
): Promise<ParseRecipeResult | null> {
  log.warn(
    { url, reason, aiAttempted, parserPath: "jsonld-fallback" },
    aiAttempted
      ? "AI extraction failed; attempting the JSON-LD fallback"
      : "AI extraction was not attempted; attempting the JSON-LD fallback"
  );
```
At `:432` capture `const aiAttempted = aiEnabled && (await isPageLikelyRecipe(html));`, use it for
the branch, pass it at `:454`, and pass `true` at `:398`. Replace the `:458` default with something
honest, e.g. `"structured-failed-ai-skipped"` when `!aiAttempted`.

**Files:** `packages/api/src/parser/legacy.ts` (27 lines), `packages/api/src/parser/microdata.ts`

**Are there two JSON-LD implementations?** **No — and this is the important correction.** Both

need trimming; `import-flow.test.ts:301` is the only test that sets it `true`.
`packages/shared-server/src/config/server-config-loader.ts:176`
(`shouldUseLegacyRecipeParserRollback`) has **zero callers repo-wide** and dies with it — flagged
for the shared-server reviewer, out of my area.

**Confidence it should be deleted rather than retained as a policy lever: MEDIUM** — this is a

### WR-04: the live AI path misclassifies an empty generation as `VALIDATION_ERROR`; the only "empty response" code lives in the dead executor

**File:** `packages/api/src/ai/recipe-parser.ts:124-130`

```ts
const validation = validateExtractionOutput(jsonLd);
if (!validation.valid) {
  aiLogger.error({ url, ...validation.details }, validation.error);
  return aiError(validation.error!, "VALIDATION_ERROR");   // :129 — always VALIDATION_ERROR
}
```

`validateExtractionOutput`
(`packages/api/src/ai/features/recipe-extraction/normalizer.ts:229-232`) distinguishes the two
cases correctly in its **message**:

```ts
if (!output || Object.keys(output).length === 0) {
  return { valid: false, error: "AI returned empty response" };   // :231
}
```

…but `recipe-parser.ts:129` collapses both outcomes into `VALIDATION_ERROR`. The `EMPTY_RESPONSE`
code exists, is in `RETRYABLE_AI_EXTRACTION_CODES` (`parser/index.ts:99`), and is emitted **only by
the unreachable `ai/core/executor.ts:125`** (see WR-03).

**Consequence.** `parser/index.ts:180` logs
`{ code: result.code }` → `VALIDATION_ERROR`, and 27.1-01's own docblock (`:84-87`) says
`VALIDATION_ERROR` "fires only for genuinely unusable output (no name, or zero metric
ingredients/steps)". That is now false: the reasoning-token-exhaustion failure mode this phase exists
to rescue — an empty generation — reports as `VALIDATION_ERROR` too. At a 7% live success rate, the
one code that would have told the operator "the model returned nothing" is unreachable, and the code
that does fire says the opposite of what happened.

Retry behaviour is unaffected (both codes are retryable), so this is a **diagnosis** defect, not a
behaviour defect — which is precisely why it has survived.

**Fix:**
```ts
// normalizer.ts — distinguish the cases structurally, not by message string
if (!output || Object.keys(output).length === 0) {
  return { valid: false, error: "AI returned empty response", empty: true };
}

// recipe-parser.ts:126-130
if (!validation.valid) {
  aiLogger.error({ url, ...validation.details }, validation.error);
  return aiError(validation.error!, validation.empty ? "EMPTY_RESPONSE" : "VALIDATION_ERROR");
}
```
