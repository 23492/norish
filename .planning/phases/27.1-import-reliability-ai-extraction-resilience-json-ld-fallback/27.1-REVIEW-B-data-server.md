### CR-03: Four job-status probes in `pending.ts` apply no ownership or cookbook check

**File:** `packages/trpc/src/routers/recipes/pending.ts:50-66`, `94-110`, `112-128`, `158-174`

Confirmed as you flagged. `isNutritionEstimating`, `isAutoTagging`, `isAutoCategorizing`
and `isAllergyDetecting` all take an arbitrary `recipeId: z.uuid()` from an authenticated
caller and answer purely from the BullMQ queue:

```ts
// pending.ts:100-102 (isAutoTagging) — representative of all four
const isActive = jobs.some(
  (job) => job.data.recipeId === input.recipeId
);
```

No `job.data.userId`, no `job.data.householdKey`, no `ctx` comparison at all. Contrast
the sibling `getPending` at line 31-34, which *does* clamp
(`isOwnerScoped ? job.data.userId === ctx.user.id : job.data.householdKey === ctx.householdKey`,
documented as PENDING-ISO-01 / D-27.1-12).

**Disclosure:** a boolean oracle over any recipe UUID in any cookbook — "is recipe X
currently being AI-processed on this server". Combined with `getPending` (which returns
`recipeId` for your own cookbook), this leaks activity for *other* households' recipes.
Low-severity information disclosure, but it is a real per-cookbook boundary hole and it
sits directly beside a comment claiming the boundary is enforced.

**This is a security gap, not dead code — do not delete these procedures.**

**Fix:** apply the same clamp `getPending` uses:
```ts
const isActive = jobs.some(
  (job) =>
    job.data.recipeId === input.recipeId &&
    (isOwnerScoped
      ? job.data.userId === ctx.user.id
      : job.data.householdKey === ctx.householdKey)
);
```
Then adversarially verify: temporarily remove the clamp and confirm
`packages/trpc/__tests__/recipes/pending-isolation.test.ts` goes red. If it stays green,
the test does not cover the four probes and must be extended before the fix lands.

### CR-04: `getPendingAutoTagging` / `getPendingAllergyDetection` use an `OR` that defeats the owner-only policy

**File:** `packages/trpc/src/routers/recipes/pending.ts:79-84` and `141-145`

```ts
// pending.ts:80-83
.filter(
  (job) =>
    job.data.userId === ctx.user.id || job.data.householdKey === ctx.householdKey
)
```

`getPending` (line 31-34) branches on `policy.view === "owner"` and, when the server
policy is owner-only, restricts strictly to `job.data.userId === ctx.user.id`. These two
list procedures ignore the policy entirely and **OR in** the household key. Under a
`view: "owner"` server policy they therefore return the `recipeId`s of *household-mates'*
recipes — precisely the disclosure the `getPending` clamp exists to prevent.

`ctx.householdKey` is `household?.id ?? user.id` (`packages/trpc/src/middleware.ts:38`),
so for a user with no cookbook the OR degenerates harmlessly; for any user *in* a
cookbook it is a strictly wider grant than `getPending` allows.

**Fix:** route both through the same policy-aware predicate as `getPending`:
```ts
const policy = await getRecipePermissionPolicy();
const isOwnerScoped = policy.view === "owner";
const recipeIds = jobs
  .filter((job) =>
    isOwnerScoped
      ? job.data.userId === ctx.user.id
      : job.data.householdKey === ctx.householdKey
  )
  .map((job) => job.data.recipeId);
```
Note this is a *narrowing* of an existing grant — it must not be applied in reverse.

### WR-02: Account deletion orphans recipes and their media (FK is `SET NULL`, not cascade)

**Files:** `packages/trpc/src/routers/user/user.ts:279-318`,
`packages/db/src/repositories/users.ts:347-349`,
`packages/db-schema/src/schema/recipes.ts:28-33`

`deleteAccount` deletes avatars, then calls `deleteUser` → a bare
`db.delete(users).where(eq(users.id, userId))`. Both `recipes.user_id` **and**
`recipes.household_id` are `onDelete: "set null"`.

Consequence for a **personal** recipe (`household_id` already NULL): after deletion the row
has `user_id = NULL` **and** `household_id = NULL`. `canAccessResource`
(`packages/auth/src/permissions.ts:97, 113`) then returns `false` for every caller —
`userId === ownerId` can never match `null`, and the `household`/`everyone` branch
short-circuits on `resourceHouseholdId === null`. The recipe becomes permanently
invisible and undeletable, and its `uploads/recipes/<id>/` directory is **retained**,
because the media-reconciliation job prunes "recipe directories not in `recipes.id`"
(`packages/db/__tests__/server/db/cleanup/cleanup-workflows.test.ts:103`) — and the row
still exists.

Consequence for a **household** recipe: it stays fully visible to the remaining cookbook
members with a null author. That may be intended (recipes survive the member leaving) but
it is nowhere stated, and it is a data-retention question for a "delete my account" action.

**Fix:** decide the policy explicitly and implement it in `deleteAccount` *before*
`deleteUser` — either (a) delete the user's personal recipes and their media, or
(b) reassign them. Add a db test that asserts no `recipes` row can end up with both
`user_id` and `household_id` NULL.

### WR-03: `updateRecipeWithRefs` NULLs `cook_source` but leaves `cook_confidence` / `cook_review_needed` stale
